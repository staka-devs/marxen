# 提案の取込と文書毎の承認結果で隔離審査を完成させる

- 状態: 採用
- 日付: 2026-10-08
- 関連 Issue: #5（隔離は #8、AI 契約は #7、基盤は #4）

## 背景・選択肢

雛形の隔離審査では取込命令がなく、承認戻り値が旧形のままだった。提案を原文へ直接書く方法と、検証済み提案文を作業複写に取り込んでから差分承認する方法を比較した。承認を一括成功として扱う方法と、文書毎の適用結果として扱う方法を比較した。

## 決定と理由

- 完了提案は方式付きで `stageProposal(copyId, proposal, mode)` により作業複写へ取り込む。質問（ask）は表示のみで取込を拒否する。書換・生成は単一範囲の選択でのみ exact 置換し、workspace 修正は構造化 patch 形式でのみ受ける。範囲・改訂・抜粋の不一致は actionable な誤りで拒否する。
- 承認は `ApproveResult`（文書毎の適用・改訂・誤り・巻戻し有無）で受け、適用文書は snapshot を取り直して原文表示を揃え、部分適用を全部成功に見せない。失敗時は新規複写で再同期する。却下・取消は原文と磁気記録を変更しない。
- 実行開始時に Rust が複写を pin し、再開・完結・打切の settlement 時にのみ release する。実行中の承認・却下・取消は io 誤りで拒否され、取消要求だけでは実行を完結させない。複写は settlement まで保持する。資格情報は OS 保管に置き、localStorage には非秘密の設定だけを残す。

## 結果・制約・確認方法

- Vitest で正確な範囲登録・提案取込（ask 拒否を含む）・差分・文書毎の承認結果・却下・取消・古い基準の拒否を模擬 IPC で検証する。Playwright では読取専用と改訂不変を製品ビルド（1425 番）で検証する。Rust は範囲 exact・pin・settlement・実 preflight の統合で検証する。
- 未検証として残す。各 OS の実 WebView における実行・取消・表示の確認。実接続の AI 実行。いずれも成功と記載しない。
