# ADR-0136: アカウントの独立した認証欄と既存ログインの読取りを提供する

- 状態: 採用
- 日付: 2026-10-16
- 関連: #103、#102
- 変更する判断: [ADR-0132](ADR-0132-全プロバイダーの管理アカウントと使用量をホストごとに分離する.md) の認証入力・既存ログイン・managed path の対応範囲

## 背景と選択肢

MiniMax と OpenCode Go には API キーとブラウザーの完全な Cookie ヘッダーを独立して設定する経路が必要である。Grok と Cursor は利用者の既存 CLI / IDE ログインを再利用できる必要がある。また macOS の `/var` と `/private/var` は通常のシステム別名であり、私有ファイルの管理ルート内の symlink 攻撃と同一に扱えない。

別の保存 API・旧形式用の変換層・秘密値を画面へ読戻す方法は採用しない。未公開コンソール API の build 固有 server-function hash を固定して自動実行する方法も採用しない。

## 決定と理由

- 保存操作は `save(account, credentials)` の 1 本とし、write-only `AccountCredentialPatch` の `secret` / `apiKey` / `cookie` を provider ごとに検証する。MiniMax / OpenCode Go は API キーと Cookie を OS ストアの同一 envelope 内で独立更新する。欄の省略は維持、明示的な空文字は削除である。snapshot は存在の boolean だけを返す。秘密値の旧 raw API-key 形式の自動変換は実装しない。
- API キーがある場合は Cookie を送信しない。API キーの失敗から別の認証へ自動切替しない。Cookie は固定の provider host のみへ送り、全 Cookie 名と値を維持する。`Cookie:` のヘッダー名だけを除去し、`__Host-console_session` を `auth` に書き換えない。改行・不正な Cookie pair を拒否する。
- MiniMax は global / CN の固定 endpoint を選択できる。Cookie 経路では group ID を `X-Group-Id` として送り、configured models は返却された model 名を完全一致で絞るために使う。未知の残量や金額を推定しない。
- OpenCode Go の Cookie 経路は `GET /console/api/go/status` と `x-org-id` を使用する。workspace ID が空なら、認証済み `/console` の SSR records / workspace links、または同一 origin の workspace redirect から検出する。応答を 256 KiB、試行を 4 workspace、全体を 15 秒に制限する。検出できない場合は明示 ID を求める。使用量の応答には実際に採用した workspace ID を付ける。quota meter の割合を金額と表示しない。
- Grok は明示操作で `~/.grok/auth.json` の検証済み first-party issuer entry の `key` / `user_id` を読む。無関係な IdP の保存値を xAI へ送らず、refresh token を使わず、ログインを書き換えない。
- Cursor は OS ごとの CLI `auth.json` を優先し、不在の場合は IDE の `state.vscdb` の固定 `cursorAuth/accessToken` key を読み取る。SQLite は bundled rusqlite の read-only / no-create / no-follow flags、固定 SELECT、値上限と短い busy timeout を使用する。TEXT / BLOB の両形式を扱い、CLI の既存 token が無効・失効なら別のログインへ切り替えない。macOS の既知 Keychain entry は最後の読取り候補とする。ブラウザーの認証 DB は読まない。
- managed root 自体とその内側の全 path component の symlink を拒否する。root より上の信頼済みシステム path は alias を許し、macOS の標準パスを壊さない。私有ファイルを書き込む前の検査と nested-link fixture を維持する。

## 結果と確認方法

全設定が Rust の保存・選択・削除と同じ境界を通り、資格情報は snapshot・localStorage・エラー本文へ出ない。public API は型付き保存操作だけになり、別名の保存 API や migration は存在しない。

検証は人工 Cookie / token / SQLite / console response fixture と UI 操作で行う。provider 内部 API の安定性、実アカウント通信、各 OS の既存ログイン・Keychain・WebView の成功は fixture から推定しない。公式 source URL、入力形式、対応しない応答の扱い、実施結果は [provider-accounts.md](../provider-accounts.md) に記載する。
